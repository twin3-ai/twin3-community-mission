# twin3 $PoC Soulbound ERC-20 功能規劃

版本：V1 草案  
狀態：功能定義，尚未進入智能合約實作

## 1. Token 定位

`$PoC` 是 twin3 用來記錄「真人所完成之可驗證貢獻」的代幣。

它同時具備兩個特性：

- **Fungible**：每一單位 `$PoC` 的價值與計算方式相同，可以累加、扣除與比較。
- **Soulbound**：代幣綁定於通過 twin3 身分驗證的使用者，不可轉讓、買賣、贈送或存入其他人的錢包。

因此，`$PoC` 應定義為：

> 可被 ERC-20 工具讀取，但禁止使用者間轉移的貢獻憑證。

## 2. 核心功能

| 功能 | 說明 |
|---|---|
| 餘額查詢 | 使用者可查看自己的 `$PoC` 總額。 |
| 總供應量查詢 | 公開顯示系統已發出的 `$PoC` 總量。 |
| 貢獻鑄造 | 只有 twin3 授權的結算系統，才能依已驗證的貢獻發放 `$PoC`。 |
| 批次結算 | 支援定期結算多位使用者，並保留每筆來源與事件編號。 |
| 禁止轉移 | `transfer`、`transferFrom` 與授權他人動用代幣的功能必須停用。 |
| 銷毀 | 未來兌換、消耗、撤銷錯誤發放時，可依規則銷毀 `$PoC`。 |
| 稽核調整 | 更正餘額時必須留下原因、操作者、時間與原始事件，不可靜默改數字。 |
| 暫停機制 | 發生安全事故時，可暫停鑄造、銷毀與遷移，不影響公開查詢。 |

## 3. 身分與資格

`$PoC` 必須綁定於 twin3 的真人身分，而不只是單一錢包地址。

開始累積 `$PoC` 的基本條件：

1. 使用者已綁定 Discord 身分。
2. 使用者持有 Twin Matrix SBT。
3. 貢獻事件可以歸因到該使用者。
4. 該事件尚未被結算，避免重複發放。

不同角色可使用不同的計算規則，例如：

- Experiencer `$PoC`
- Builder `$PoC`
- Connector `$PoC`
- Creator `$PoC`

使用者的 Token 餘額是累積結果；角色、任務、來源與計算明細則保留在可稽核的 PoC 帳本中。

Community Mission Quiz 的獎勵歸入 **Experiencer `$PoC`**。

## 4. 非轉移規則

使用者不能：

- 將 `$PoC` 傳給其他使用者。
- 在交易所或流動性池交易 `$PoC`。
- 授權第三方錢包代為轉移 `$PoC`。
- 跨鏈橋接 `$PoC`。
- 透過換錢包規避身分綁定。

系統允許的餘額變動只有：

- 經驗證貢獻後鑄造。
- 合法兌換或消耗後銷毀。
- 有完整稽核紀錄的更正。
- 通過身分驗證後進行錢包遷移。

## 5. 錢包遷移與復原

當使用者更換正式錢包時，不應直接使用 ERC-20 轉帳。

建議流程：

1. 使用者重新證明 Discord、Twin Matrix SBT 與新錢包的控制權。
2. 系統確認新舊錢包屬於同一個 canonical identity。
3. 舊錢包的 `$PoC` 被鎖定或銷毀。
4. 在新錢包恢復等量 `$PoC`。
5. 全程留下遷移紀錄，且同一筆遷移只能執行一次。

## 6. 未來兌換

未來規劃可讓 `$PoC` 按政策 **1:1 兌換 twin3 Token**。

建議採用「銷毀 `$PoC`，再發放 twin3 Token」的方式，避免同一份貢獻被重複使用。

V1 只保留兌換介面與稽核能力，暫不啟用：

- 實際兌換。
- twin3 Token 發放。
- 市場價格或投資用途。

## 7. 公開資訊與隱私

可公開：

- `$PoC` 餘額。
- 角色分類餘額。
- 排名與等級。
- 已驗證貢獻的摘要。
- Token 總供應量。

不應直接公開：

- 私人驗證資料。
- OAuth Token。
- 錢包簽名內容。
- 內部風險標記。
- 可識別個人的完整審核證據。

## 8. V1 不處理的項目

本版本不決定：

- 發行總量與 Tokenomics。
- 價格、募資或交易所上架。
- 鏈與部署地址。
- 小數位數。
- 管理員、多簽與治理架構。
- 兌換開放時間。
- 智能合約升級方式。

## 9. V1 建議結論

第一版應把 `$PoC` 做成：

> **非轉移、可稽核、與真人身分綁定的 ERC-20 貢獻憑證。**

先確保貢獻來源正確、不能重複結算、不能交易與不能冒領，再進入 Tokenomics 和正式智能合約設計。
